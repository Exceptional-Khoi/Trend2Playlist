# Chiến dịch 2 — thiết kế Cloud E2E

Thiết kế ban đầu 08/11, cập nhật theo sản phẩm ngày 10/11/2026. Phiên bản kiểm thử được xác định bằng SHA, working tree và hash từng file runner ghi trước/sau; không cố định nhận định main/dev cũ. Generic image digest không thay thế bằng chứng source ConfigMap. Namespace hiện hữu chỉ được quan sát trong chế độ read-only; ghi/fault cần scope test riêng đã được chủ môi trường cho phép.

## Topology và đường dữ liệu thực

Profile test dùng ba Kafka KRaft broker (RF3/minISR2), HDFS NameNode và hai DataNode (replication2), Elasticsearch một node, Spark master/worker/driver, FastAPI và observer. Mọi dịch vụ có state đều riêng namespace, own Kafka DNS, ES index instance và HDFS `/qa/<run-id>`. Không dùng chung state với `music`. Dùng emptyDir có giới hạn; không PVC, disk mới, LoadBalancer, nodepool hay IAM. Đây là profile thu nhỏ: không suy rộng thành HA ES hay node-loss durability của production.

`crawler/src_apple.py` gọi HTTP fixture nội bộ có schema Apple (chỉ URL nguồn đổi trong process test), producer thật → Kafka thật → `ingest_raw` ghi HDFS và `insight_raw` ghi ES raw → `/api/insights/*`. Bình luận → HDFS và typed `music-comments` → selector/report API; owned stack không có model key nên report phải 503, không phát sinh phí model. Events dùng cho `rt_plays` và HDFS backend, không vào insight raw và không còn `/api/listen`. CE-013 chạy batch thật từ HDFS và kiểm chứng REST search riêng.

Recommendation vẫn có query/backend legacy, dashboard hiện hành là bốn insight. Crawler `crawler/` là runtime của deployment; `crawlers/` là các công cụ khác/legacy, không giả định cùng pipeline. Batch cũ và deployment hiện hữu phải được đánh giá theo source đang mount, không gán lỗi trực tiếp cho `dev` khi source khác.

## Oracle và adversarial scenarios

Không import hàm insight để tính expected. Lifecycle dựa source periods/completeness; membership đếm playlist ID khác nhau, kể cả unknown/mirror; country dùng thứ hạng và chart size độc lập. Legacy Jaccard/exposure có unit regression riêng, không gán vào API hiện tại. Kafka topic/partition/offset và raw bytes là oracle transport. Cùng event_id ở hai partition kiểm business double-count của `rt_plays`; capture cũ ở microbatch sau kiểm latest-state regression.

Checkpoint commit + offset log chứng minh Spark đã commit qua records cần kiểm tra, không suy luận chỉ từ pod Ready. HDFS đọc Parquet thật qua WebHDFS/pyarrow; ES mget đối chiếu doc ID và raw bytes; API đi HTTP thật từ observer. Image IDs, revision, ConfigMap và mounted file hashes được lưu. Event-time cửa sổ phút tách khỏi Kafka ingest timestamp. Polling bounded, không sleep để đoán readiness. Các case dùng unique keys; thứ tự cố định vì watermark là state dùng chung trong stack test. Điều này được khai báo, không gọi là test-order independence hoàn toàn.

Recovery chỉ restart Pod có đúng namespace, run label và UID; ES outage/latency qua proxy đến ES thật. Không xóa shared pods/PVC hay sửa production source. Pod readiness RTO khác data recovery; không tuyên bố exactly-once chỉ dựa vào số lượng. Các case tải CP-001/CP-002 hiện là thiết kế deferred, chưa có executable test; không coi một lần chạy smoke ở chế độ performance là đã đo tải/SLA.

## Safety, cost, cleanup

Scope JSON bắt buộc explicit context/project/cluster/zone/run; xác minh GKE endpoint và nodepool autoscale disabled trước write. Không dùng ambient gcloud project đang trỏ project khác. Headroom và node metrics guard; dừng khi node memory >90%, CPU >95%, node inventory thay đổi hoặc workload baseline restart/readiness xuống. Quota requests CPU3/memory7Gi, limits CPU8/memory14Gi, pods18; max runtime3600s. Không thay cluster config. Resource journal có UID; cleanup chỉ own resources, kiểm toàn bộ namespace metadata rồi mới xóa namespace, giữ lại nếu còn object không thuộc run. Thu log trước cleanup. Không log Secret data/token.

## Giới hạn thiết kế đã biết

Sáu bài RO-001..006 dùng namespace hiện hữu theo chế độ read-only: health API/ES, Kafka seek exact offset với auto-commit=false, chart REST/ES consistency, bốn insight HTTP, worker stability và latest batch completion/logs. Chúng kiểm source đang triển khai (hash/digest lưu riêng), không gọi là E2E `dev`, không ghi data/checkpoint. Hai port-forward được đóng khi kết thúc. Thay đổi phạm vi này không bỏ qua safety guard hay tự restart workload gốc. Rollout sửa workload hiện hữu phải được chủ môi trường cho phép riêng.

Không kiểm node termination/zone outage, corrupted shared checkpoint, IAM changes, disk/PVC loss, long soak, autoscaling hoặc unbounded stress. Hai case public-source PS-001/PS-002 opt-in chỉ gọi tối đa một feed Apple/Spotify mỗi case; các E2E pipeline khác dùng controlled source. Không chứng minh đầy đủ external availability/anti-bot, ES multi-node recovery hoặc durable storage khi node mất vì emptyDir. Các case bị chặn phải BLOCKED, không PASS. Exact watermark lateness, recommendation, rolling upgrade, simultaneous batch/realtime publication, incompatible schema và full-network partition chưa có executable coverage đầy đủ. Normal pytest không mở kết nối cloud/public feed.
## NameNode metadata checkpoint regression (CH-001)

This additional real-service regression checks a separate failure mode from Spark checkpoint recovery: primary NameNode edit logs can fill its metadata PVC without periodic fsimage compaction. The test creates sixteen owned HDFS directories, starts the source SecondaryNameNode manifest against the owned NameNode, waits for the primary fsimage transaction to advance, and checks that all sixteen entries survive. Both owned nodes use accelerated test policy (10s period,10transactions,5s checks) so a tiny fixture can pass the primary's normal upload timing/transaction gate; production XML and upload validation remain unchanged. Initial tests demonstrated HTTP409 primary rejection despite a secondary command reporting success. The physical primary-image assertion is retained. It records image IDs, mounted configuration, manifest hash and checkpoint logs. A TCP-ready checkpoint pod alone is insufficient to pass. The test remains cloud opt-in, uses temporary checkpoint storage, and does not certify the production15-minute scheduling interval, long-term disk capacity or HA. An independent read-only Kafka/ES sample now prefers descending physical document order to reduce retention misses; exact offset payload equality is unchanged.
